# qa-rules.md

이 저장소에서 QA 작업을 진행할 때 따르는 워크플로우입니다.

## QA 리스트 형식

- QA 항목은 **AS-IS / TO-BE** 형식으로 전달된다.
  - **AS-IS**: 현재 잘못된/문제가 있는 동작
  - **TO-BE**: 수정 후 기대하는 동작
- 각 항목은 하나의 task로 취급하고, 여러 항목이 한 번에 오면 항목 단위로 순서대로 처리한다.

## 워크플로우

### 1단계 — QA 진행

- 요청받은 QA 항목의 AS-IS/TO-BE를 확인하고, 해당 항목에 대한 task를 체크한다.
  - QA 항목 목록과 상세 내용은 `docs/qa/QA_LIST.md`에 기록되어 있다. 작업을 시작하면 해당 항목의 상태를 `대기 → 진행중`으로, 완료 후 검증까지 끝나면 `진행중 → 완료`로 갱신한다.
- 관련 코드(컴포넌트/타입/API 호출부 등)를 먼저 찾아 현재 동작이 AS-IS 설명과 일치하는지 확인한다.
  - 일치하지 않으면(이미 고쳐져 있거나, 원인이 다르면) 임의로 추정해 진행하지 말고 사용자에게 확인을 요청한다 (`CLAUDE.md`의 "추측 금지" 원칙).
- TO-BE에 맞춰 수정 작업을 수행한다.

### 2단계 — 검증(재테스트)

- 수정이 끝나면, **TO-BE 내용이 실제로 적용되었는지**를 반드시 다시 테스트로 검증한다. 수정했다는 사실만으로 완료 처리하지 않는다.
- 검증 방법:
  - UI/프론트 변경: 로컬 dev 서버(`npm run dev`)에서 실제 화면을 확인하거나 Playwright 등으로 골든 패스 + 관련 엣지 케이스를 확인한다.
  - 타입/로직 변경: `npm run build` 또는 `npm run lint`로 타입 에러·린트 에러 여부를 확인한다.
  - 테스트만으로 확인이 불가능한 부분(예: 실제 백엔드 연동, 눈으로만 판단 가능한 스타일)은 "확인 못함"을 명시적으로 알리고, 사용자에게 직접 확인을 요청한다. 확인 없이 "완료"로 보고하지 않는다.
- 검증 결과 TO-BE와 실제 동작이 다르면, 완료 처리하지 않고 원인을 다시 분석해 재수정한다.

## 보고 방식

- 각 QA 항목 처리 후 다음을 간결히 보고한다:
  - 무엇을 고쳤는지 (AS-IS → TO-BE 기준)
  - 어떻게 검증했는지 (실행한 테스트/확인 방법)
  - 검증 결과 (통과 / 미확인 항목 있음)
