# git-rules.md

이 저장소에서 Git을 사용할 때 따르는 규칙입니다.

## 브랜치 구조

- **`main`**: 배포용. 항상 안정 상태 유지 (Vercel 자동 배포 트리거). 직접 push 금지, `develop`에서 충분히 검증된 뒤에만 반영
- **`develop`**: 통합 브랜치. 기본 작업 브랜치이자 default branch
- **`feature/*`**: 기능 단위 브랜치. `develop`에서 분기, `develop`으로 머지

## 브랜치는 기능 단위로 나눈다

프론트/백엔드 기준(`feature/frontend-login`, `feature/backend-login`)이 아니라 **기능 단위**(`feature/login`)로 나눈다. 하나의 기능 브랜치 안에서 프론트(Next.js)와 백엔드(Nest.js)를 함께 작업한다.

- 이유: 프론트 폼을 만들면서 백엔드 응답 구조가 실시간으로 확정되는 게 자연스럽고, PR 하나가 "기능 전체"를 리뷰 단위로 만듦
- 예외: DB 마이그레이션만, UI 리팩토링만처럼 작업 특성상 한쪽만 건드리는 경우는 자연스럽게 그 폴더만 건드리는 브랜치가 됨 — 이건 억지로 나눈 게 아니라 결과일 뿐

## 인증/세션 관련 작업

`feature/auth-*`로 반드시 격리해서 작업한다. 배포 전 충분한 테스트 없이는 사고 위험이 큰 영역이므로, `develop`에 머지하기 전 별도 검증 단계를 거친다.

## 커밋 메시지

한국어로 작성한다.

## 레포 구조

프론트/백엔드로 레포를 분리하지 않고 **모노레포**를 유지한다 (`apps/web`, `apps/api`). 이유와 재검토 조건은 `.claude/rules/work-02-nest.js.md` 참조 — 요약하면 1인 풀스택 + 결합도 높은 프로젝트에서는 레포 분리로 얻는 이점이 없고, 팀원이 프론트/백으로 역할이 명확히 나뉘는 시점에 재검토한다.

## PR / 머지

- PR은 기능 단위로 열고, `develop`으로 머지한다
- `main` 머지는 배포 시점에만, `develop`이 충분히 검증된 뒤 진행한다
- 팀원 합류 이후에는 `main`에 branch protection rule(직접 push 금지, PR 필수)을 적용하는 것을 고려한다 — 지금은 1인 작업이라 강제하지 않지만 습관은 미리 들여둔다

## 비고
